# Chapter 20 — Collaboration Through Operational Memory

## What you will learn

Chapter 8 used memory with one Function. Here you will use scope deliberately —
to give two Functions a shared standard while keeping each one's private
working notes to itself.

Chapter 19 established that a shared Worker carries nothing between Functions.
Memory is the channel that does, and scope is the control on it.

[Chapter 17](./Chapter_17_Events_as_Organisational_Communication.md).

## Choosing scope

The question to ask is not "is this true?" but **"who is harmed if this is
wrong?"**

- **One Function** — working practice, a preference, something specific to how
  that responsibility is carried out. Wrong here, it misleads one Function.
- **The business** — a standard everything should meet. Wrong here, it misleads
  everything at once.
- **Everything on this computer** — crosses businesses entirely. Rarely correct,
  and worth being deliberate about, because a note written for one client's work
  will turn up in another's.

Prefer the narrowest scope that does the job. Widening a note later is easy;
noticing that a too-wide note has been quietly shaping every Function's output
is not.

## Memory is not a conversation

Two Functions sharing a note are not talking to each other. Memory is
context handed to Workers when they run — it is passive, and nothing is notified
when it changes.

If one Function needs another to *act*, that is an Event (Chapter 17). If it
needs it to *know*, that is memory. Using memory where an Event belongs produces
a system where nothing appears to happen for no visible reason.

## What not to share

Everything Chapter 8 said still applies, and matters more at wider scope:
no credentials, no personal data, no confidential material, no guesses recorded
as facts.

Scope controls **reach, not confidentiality**. Narrowing a note to one Function
does not hide it — anyone using this copy of Arturo can read every note in it.

## Removing a note that has spread

```text
/memory
```

Answer `3` and pick it.

Removing a note stops it being given to future work. It does not retract the
work it already shaped. If a wrong note has been in a wide scope for a while,
removing it is the start of the fix, not the whole of it — look at what was
produced while it was there.

## Completion check

You have finished when:

- one note applies to the whole business and one to a single Function;
- `/memory` shows both with their scope; and
- you can say why memory is not the way to make another Function do something.
