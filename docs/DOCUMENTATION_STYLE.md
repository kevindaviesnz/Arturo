# Arturo documentation style

Use this guide when writing or reviewing Arturo documentation.

## Write for a new reader first

- Explain a new Arturo term before using it.
- Prefer a short sentence to a sentence with several clauses.
- Prefer a familiar word when it has the same meaning.
- Give a small example after an abstract idea.
- Keep paragraphs focused on one point.
- Use the [glossary](./GLOSSARY.md) instead of redefining a term differently.

## Use Arturo terms carefully

Capitalise named Arturo concepts:

- Enterprise;
- Business Function;
- Runtime;
- Job;
- Worker;
- Governance;
- Event;
- Operational Memory; and
- Human Task.

Do not use a difficult term when a plain one is clearer:

| Avoid when possible | Prefer |
|---|---|
| utilise | use |
| instantiate | create |
| invoke | run or call |
| leverage | use |
| ingest | receive or read |
| facilitate | help |
| terminate | stop or end |
| provenance | source, followed by “provenance” only when needed |
| consequential | important or high-impact |

Some technical terms, such as `deterministic`, are important. Define them on
first use.

## Make commands safe to copy

- Do not include the `arturo ›` or `os>` prompt.
- Quote names and sentences that contain spaces.
- Use `<job-id>` only as an obvious placeholder.
- State what must exist before the command runs.
- State what the command changes.
- Show how to check the result.
- Show a safe recovery step for likely failures.

## Separate fact from model output

Never imply that a completed Job is correct merely because it completed.

Use clear labels:

- **Supplied fact** — entered by the user for this exercise.
- **Human assertion** — entered by a person but not independently checked.
- **Model suggestion** — generated by an AI and not verified.
- **Verified evidence** — checked against a suitable named source or process.

## Separate the current product from future design

Use one of these labels:

- **Supported now** — the command is in primary `/help` and has current tests.
- **Current approximation** — current commands can demonstrate part of the
  idea, with stated limits.
- **Target architecture** — planned design that is not implemented.

Command-shaped text is not enough to prove that a feature exists.

## Keep specialist documents accurate

Legal, security, medical, financial, and architecture documents may need
specialist terms. Add a plain-language summary, but do not replace a precise
term with an inaccurate one.

Legal working drafts must continue to say that they are not legal advice.

## Review checklist

Before merging documentation, check:

- Can a new reader explain the purpose after the first paragraph?
- Are unfamiliar words defined or linked?
- Are sentences reasonably short?
- Are examples synthetic and safe?
- Are commands supported?
- Are expected changes and non-changes clear?
- Are current and future features separated?
- Are AI claims labelled?
- Are links valid?
- Does the document avoid secrets and personal information?
